# Compatibilité IPC KiCad 10.99-5583 — 21 octobre 2026

Autorisation : corriger la compatibilité, valider le fonctionnement IPC et
installer le plugin, sans modifier KRT. Développement 0.1.5 ; aucun ZIP créé.

## Diagnostic confirmé avant correction

La lecture des classes de nets échouait avec kicad-python 0.8.0 : sa commande
`GetNetClasses` ne contient aucun champ et n'identifie donc pas le projet.
La nightly demande désormais `ProjectSpecifier project = 1`.
Fournir seulement le document annoncé par KiCad ne suffit pas :
`GetOpenDocuments` expose `GetProjectDirectory()` sans séparateur terminal,
alors que `validateProject` compare à `GetProjectPath()`, qui l'inclut.
Les trois sondes réelles ont distingué les causes : requête vide refusée,
projet avec chemin annoncé refusé, même projet avec antislash terminal accepté
(classes `Default`, `Power_1`, `Power_2`). Un slash terminal seul échoue sous
Windows sur cette version.

Sources officielles consultées au commit exact de la nightly
`6a6fb7561d7d35f3a2324326f22d19c01c9f7462` :

- [Contrat GetNetClasses](https://gitlab.com/kicad/code/kicad/-/blob/6a6fb7561d7d35f3a2324326f22d19c01c9f7462/api/proto/common/commands/project_commands.proto#L28).
- [Validation du projet](https://gitlab.com/kicad/code/kicad/-/blob/6a6fb7561d7d35f3a2324326f22d19c01c9f7462/common/api/api_handler_common.cpp#L113).
- [Document annoncé](https://gitlab.com/kicad/code/kicad/-/blob/6a6fb7561d7d35f3a2324326f22d19c01c9f7462/pcbnew/api/api_handler_pcb.cpp#L247)
  et [deux représentations du chemin](https://gitlab.com/kicad/code/kicad/-/blob/6a6fb7561d7d35f3a2324326f22d19c01c9f7462/common/project.cpp#L179).

Le RAG a été interrogé en premier. La documentation
[Project 0.8](https://docs.kicad.org/kicad-python-0.8.0/project.html), indexée
le 16 octobre, et l'instantané du projet `main@c20178653` du 17 octobre
ne couvrent pas cette évolution de la nightly. Les sources exactes et
l'application installée ont donc complété ces instantanés.

La recette renforcée a ensuite révélé un second défaut préexistant :
`kipy.wrapper.Wrapper.clone()` efface l'UUID pour préparer une création.
Le pont l'employait pour modifier un via. Sur cette nightly, la réponse
à une modification sans UUID reproduisait les coordonnées demandées mais
le via de la carte restait immobile. Sonde `/B` avant correction : un via
annoncé déplacé, zéro position réellement modifiée. Vérifier l'accusé,
le nombre d'objets et Undo ne permettait pas de détecter cette absence.

## Adaptation limitée au plugin

`ipc_rules.read_net_classes` adresse le projet exact avec le séparateur natif
terminal ; le document source est conservé. Une identité incomplète ou relative
est refusée avant la requête. Les erreurs IPC se propagent sans repli sur une
requête globale ou des valeurs de règles par défaut.

Le descripteur privé reçoit `common/commands/project_commands.proto`, du même
commit KiCad que ses sources déjà distribuées. Les 13 descripteurs existants
restent identiques ; un quatorzième est ajouté. Le SDK 0.8.0 et son pool global
ne sont pas modifiés. Sources, provenance et licences sont distribuées.

Les vias sont copiés par leur constructeur protobuf, qui conserve UUID,
padstack et autres propriétés. Seule la position est changée. Les étapes
successives du même via donnent une seule modification finale. Les accusés
doivent contenir exactement les UUID demandés et leurs positions ; sinon la
transaction est abandonnée.

KRT reste **0.23.1**, commit `295f9ee197517e8323726853361eb137cc08ba9e`.
Ni ses sources ni son binaire officiel Windows ne sont modifiés :
`0c60ea2062a3023795db92bceae54e7f9dec0bf3b34bb86bda5908d651e18aad` (SHA256).
Le verrou non suivi préexistant `KRT/~test_board.kicad_pcb.lck` est conservé.
Les quatre optimisations de performance précédentes sont incluses.
